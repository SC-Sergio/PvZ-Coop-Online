# Cooperative architecture

## Current engine boundary

The original game is centered on `LawnApp::mBoard`, a single `Board*`. `Board` is a large `Widget` that owns fixed-capacity data arrays for plants, zombies, projectiles, coins, lawn mowers, and grid items. Board construction assigns itself to `LawnApp::mBoard`; much of the engine, UI, save code, and global helpers dereference that pointer. `LawnApp::UpdateFrames` invokes the `WidgetManager`, whose widget traversal calls `Update` on every registered board and draws visible widgets. This means widget registration could advance multiple boards, but it also exposes every board to global scene/result state and app-global effects. Merely creating or hiding multiple `Board`s would therefore render incorrectly and cross-wire gameplay state.

`Board::UpdateAll` now keeps the selected garden's normal widget traversal inside its scoped garden state. For an isolated, non-visible garden, it respects the widget manager's update flag and per-frame update counter, advances only `Board::Update`/simulation, and skips child-widget updates. This avoids running hidden garden controls against the currently selected `LawnApp::mBoard`. The engine path is build-covered but still needs a live in-game check with legal data.

The board and app share `mGameScene`, `mBoardResult`, `mGameMode`, `mEffectSystem`, `mPoolEffect`, `mPlayerInfo`, and game-end/save flow. `mLastLevelStats` was also app-wide; isolated Boards now bind it to a garden-owned `LevelStats` record during scoped simulation, draw, initialization, and teardown. `Board::Update` mixes presentation updates, input/cursor handling, shared effects, and the simulation calls `UpdateGameObjects`, spawning, fog, challenges, and level-end transitions. Entity objects do hold an owning `Board*`, which is a useful starting boundary. A source scan found 66 direct `mApp->mBoard`/`gLawnApp->mBoard` references and 54 `gLawnApp`/global declarations across engine sources; the wider `mBoard` token count includes per-entity and widget owner fields and is not an estimate of edits required.

## Intended separation

1. `CoopSession` owns dynamic player slots and one logical `GardenInstance` for each joined player. Empty slots own no garden. Player and garden identities are stable IDs, not player-number fields.
2. The engine adapter will associate each garden with isolated simulation state. A garden's entities, economy, wave state, ownership, defeat state, and random stream must not be shared with another garden.
3. A session tick advances every active garden independently of which garden is currently displayed. The selected garden is a presentation concern only.
4. Input becomes validated player commands. A transport interface carries versioned commands and snapshots; the authoritative host applies them through the same gameplay command path used by local play. `LocalTransportHub` is the deterministic test transport. `TcpNetworkTransport` adds a bounded, ordered stream for LAN experiments, but its identity handshake is unauthenticated and its payload is unencrypted; never expose it as an Internet-ready transport.
5. The online provider is an adapter behind transport/session interfaces. Provider identity, relay, lobby, and reconnect do not enter `Board` gameplay rules.

## Phase 1 slice in this revision

`src/Coop/CoopSession.*` is an engine-independent roster and garden-ownership core. Its garden records deliberately contain only session-level identity and terminal/tick metadata; `CoopGardenManager` creates their Board instances at match start. The unit tests establish counts 1 through 4, no garden for empty slots, capacity, duplicate identity, leave, host promotion, ready/start rules, and slot reuse invariants. The host is the first joiner, and only the host can start once all active players are ready; empty slots do not block start. During a match the model records per-owner completion or defeat: any defeated garden yields team defeat, while victory requires every active garden complete. Lobby leave is rejected after start so it cannot silently delete a playing garden. Session-level disconnect/temporary-AI/reconnecting transitions preserve the slot and garden and survive session-snapshot serialization. The manager adds heartbeat timeouts, host rejoin detection, and snapshot restore gating; automatic grace-state AI control remains unimplemented. During a match the host broadcasts disconnect and reconnecting roster states. `Board::UpdateSimulation()` now holds the existing gameplay-tick portion of `Board::Update()` behind an explicit call, while the normal widget path invokes it once in the same place as before. That method still reads app-wide scene, effect, and widget state; it is not yet proven safe as a multi-garden driver. No gameplay regression can be manually ruled out until legal game data is available.

During a co-op match, `Tab` advances the local camera to the next active garden, wraps to the first active garden, and never creates or selects an empty slot. This view change is local; the command executor still requires the local player to own the controlled garden.

`src/Coop/PlayerCommand.*` defines transport-independent gameplay intent and checks sender state, garden ownership, protocol version, monotonic command sequence, grid bounds, enum/value ranges, and target IDs. `AuthoritativeCommandProcessor` invokes an `IPlayerCommandExecutor` only after structural validation; `CoopGardenManager` implements the executor and routes supported classic-mode actions to the owned Board after checking live state through existing engine paths. On the host, local seed selection, plant placement, shoveling, sun clicks, and Cob Cannon firing use these same commands; garden ownership rejects local attempts against another player's Board. Garden viewing is a local-only presentation action: it validates the local player's owned source garden and the active target, then changes only that client's selected view; the command helpers refuse to send or broadcast it. `CoopGardenManager::AttachTransport` binds a peer to its local session player ID; guest-side Board input serializes and sends gameplay commands to the host, and the active host pumps its receive queue before each engine simulation tick. The host increments one session tick for every active garden on each game update. Accepted intents receive a fixed-size host receipt bound to each recipient, sequence, command and future garden tick (25 ticks ahead); host and clients queue the intent and apply it immediately before the Board update for that tick. A bounded per-peer FIFO retries `SendTo` failures under local backpressure. If its 256-message/512-KiB cap is exhausted, that link closes and the reconnect snapshot path handles recovery. This input delay reduces arrival-order differences for common network latency. It does not provide rollback, end-to-end receipt acknowledgements, periodic drift correction or proof that all garden simulation state is deterministic. Board-backed gameplay and the selected delay still need runtime validation with legal game data. The current fixed command/response frames and in-memory transport are not a LAN or Internet protocol stack.

`Board` now has an opt-in isolated scene/result/Yeti-seen state. Garden-scoped RAII contexts temporarily bind `LawnApp::mBoard`, `mGameScene`, `mBoardResult`, `mSawYeti`, `mLastLevelStats`, and the active PlayerInfo to the isolated board, then persist mutable fields back to that Board and restore the app state. The context also selects each garden's effects, pool effect, and random stream. Each Board owns a `LevelStats` record so its start/reset and level-end mower result do not overwrite a teammate's statistics. It scopes even when the selected garden is already bound, because nested garden updates must read and write that garden's Yeti history rather than the app-wide value. `CoopGardenManager::SelectGarden` exposes the viewed garden's Yeti state to app-level result handling and restores the prior single-player value when the session stops. Isolated non-viewed widgets skip cursor/UI work and call only their simulation update. `InitLevel`, `StartLevel`, board disposal, destruction, and construction of a secondary Board bind or temporarily assign the correct Board context; the constructor binding is needed because child `CutScene` and object instances capture `LawnApp::mBoard`. Non-isolated boards continue to read and write the original app fields, preserving the single-player path.

`CoopGardenManager` creates exactly one isolated `Board`, `EffectSystem`, pool water effect, Mersenne Twister stream, and temporary `PlayerInfo` copy for each session garden, registers those boards with the widget manager, selects one visible board, cleans up the full set, and processes each board/effect delete queue. Only the host turns Board terminal results into session garden completion/defeat and broadcasts the changed session snapshot; clients wait for that authoritative state before ending the team match. A versioned session snapshot carries the host-selected match seed; each garden derives a repeatable stream from that seed and its stable owner/garden IDs. The temporary profile ID also derives from the session seed so the engine's level-seed calculation is consistent across clients. Scoped Board update, simulation, draw, initialization, and teardown bind the app/global effect pointers, pool effect, per-garden profile, and random stream to that garden and restore the previous context afterward. Profile-backed purchases and coin rewards therefore stay within that garden's temporary copy. The ordinary app effect system, player profile, and random stream remain available to menu/UI and single-player code. `LawnApp` owns the manager, routes cooperative teardown through it, and suppresses single-board campaign end handling while the manager is active. The Game Selector's Co-op Online button opens `CoopLobbyDialog`; the dialog can create a TCP host, join a host by IP, show four dynamic player slots, select map and starting-sun difficulty, toggle ready, and start/leave. On start, `LawnApp::StartCoopMatch` maps the host-selected map to a campaign level, sets a six-plant deck, and initializes one Board per session garden. Six Classic difficulty profiles currently select starting sun; the amount receives a small adjustment based on active garden count. The app temporarily swaps in a synthetic profile and restores the original profile on exit; cooperative boards cannot write campaign saves or persist the sandbox profile. Team terminal results stop the session and return to the menu. The bootstrap currently accepts only Classic mode and sets `GAMEMODE_ADVENTURE`; in the audited `Board.cpp`, the Crazy Dave enter/talk call is confined to the Scary Potter endless-stage transition, which the current cooperative map setup does not select. Crazy Dave state remains app-global and must be revisited before adding modes that use it. Enemy balance, seed selection, and several app-global mode values remain shared, so this remains an early engine adapter and not proof of independent gameplay. Garden startup now reserves manager capacity, records each Board before widget registration, and catches setup exceptions to run manager cleanup; app/global Board, effect-system, and player-profile pointers are restored with scoped contexts. Actual multi-board execution has not been tested with legal game data.

`LobbyProtocol.*` is an engine-independent host/client lobby request path layered over `INetworkTransport`. A client sends JOIN with its transport identity and bounded display name, then READY/UNREADY or LEAVE; a host-authorized START transitions the shared session. The host publishes a versioned session snapshot after lobby changes, and clients bind the snapshot source to the expected host before applying it. The snapshot includes bounded map, difficulty, and mode IDs. Only the host can change those settings, and the host freezes them at match start. Host kick and client leave remove the lobby garden and close the corresponding peer link. `CoopLobbyController` wraps local and network transports, pumps the protocol, accepts dynamic TCP guests, and applies pre-match disconnect cleanup. `CoopLobbyDialog` exposes Create/Join/Ready/Start/Leave, LAN TCP and optional Internet WebRTC modes, map and six difficulty settings. The online mode requires an operator-supplied WSS signaling endpoint; optional STUN/TURN endpoints and the TURN shared secret are configured on the signaling server, which issues short-lived per-player credentials. No public service is deployed.

The WebRTC signaling service keeps a disconnected guest's slot reserved and stores a hash of its random resume token. `CoopLobbyController` retains the room URL/code and resume token, retries `WebRtcSignalingTransport::RejoinRoom` asynchronously once the host peer disappears, validates the returned local/host IDs, rotates its token, replaces the active transport, and exposes connection diagnostics. `LawnApp` pumps this reconnect path, while `CoopGardenManager` detects transport replacement, reattaches, and the host transitions the returning roster slot to `RECONNECTING` and starts garden recovery. The process test exercises the controller path and sends a packet over the replacement DataChannel under the existing player ID; it does not verify recovery in an initialized game Board. Signaling reconnection has only been tested against a local service, not between distinct Internet networks.

`CoopSnapshotProtocol.h` provides bounded garden-snapshot fragmentation/reassembly and peer-bound retry. `CoopGardenManager` starts that transfer on same-ID reconnect, preflights completed SAVE4 data, attempts rollback-capable restoration into the returning player's owned isolated Board, synchronizes its session garden tick, and keeps the player RECONNECTING until PVZR/PVZK confirms completion. Network-memory validation requires every known chunk, while the file reader retains optional-chunk compatibility. Connection loss during recovery returns the slot to DISCONNECTED. The manager lifecycle, successful or rolled-back load against an initialized Board, and full hostile-payload semantic coverage remain unverified; full-game reconnect must not be considered proven.

SAVE4 plant entities validate `mPlantCol` and inherited `mRow` against the fixed 9×6 board because gameplay reads them as grid-array coordinates. Seed packets require each saved `mIndex` to match its fixed slot, in addition to the cursor's active-slot check. Active mowers, selected special zombies, Stinky, portals, and rakes must resolve their required reanimation IDs before post-load repair. Zombie related/follower IDs must be null or resolve to active zombies before code paths that use `ZombieGet`. These checks run after the complete Board and effect-holder state is decoded and trigger the backup restore path on rejection.

GridItems also validate both coordinates against the 9×6 board, and lawn mowers validate their row before any gameplay loop can use them to index row state.

Challenge SAVE4 state validates its state and conveyor-seed enums, permits only an unset `(-1, -1)` or in-board challenge coordinate, and checks saved challenge/cloud reanimation IDs after effect holders load. Custom Survival's saved background is restricted to known board backgrounds.

MessageWidget styles and saved Music tune/file/burst/drum enums are range checked as well. Invalid presentation or audio state rejects the load instead of entering engine switches with unknown values.

Each SAVE4 attachment is limited to `MAX_EFFECTS_PER_ATTACHMENT` active entries, and each active entry's effect type must be a known enum before the engine's attachment switch runs. Attachment target IDs use `DataArrayTryToGet` and remain subject to cleanup if their target has expired.

After all SAVE4 chunks are applied, optional plant, zombie, projectile, coin, GridItem, and cursor entity/effect references must be null or resolve in the loaded Board/effect holders. Projectile target resolution follows its plant/zombie discriminator. This guards strict engine getters and keeps corrupt cross-entity IDs from surviving post-load repair.

Board-level ice particle IDs and each row's fwoosh reanimation IDs are also nullable references and must resolve against the app's active particle/reanimation holders before the snapshot is accepted.

Plant potted-plant indexes must be either `-1` or inside the fixed profile array capacity before any plant update or cursor rendering can use them. The check uses the array bound, not the receiving profile's populated count, so it does not assume peer profiles share garden inventory.

Zombie attachments resolve through the active attachment DataArray. Zombie target/fireball rows, ladder columns, portal columns, bungee target columns, and projectile/mower last-portal columns retain the engine's `-1` sentinel or must fall within the fixed board dimensions. Zombie umbrella state and plant subclass enums are checked during decoding.

Board presentation state is bounded before draw: fog cell looks stay in the initialized `0..19` sprite range, cell offsets remain within their initialized `-5..4` range, and fog opacity stays `0..255`. The weighted row picker retains its fixed row IDs and finite nonnegative weights/history values. Saved board result and advice enums are also checked.

`HeartbeatMonitor` adds a transport-level liveness frame handled before gameplay-command decoding. It sends bounded PING/PONG sequence frames, accepts only matching recent PONGs as activity, rate-limits new remote PINGs, and times out peers after 8 seconds. `CoopGardenManager` closes timed-out links; existing roster reconciliation marks the slot disconnected and preserves the garden for rejoin. This detects silent links but does not authenticate, apply a grace-state AI, or restore Board state. The heartbeat monitor and session loop use a real monotonic clock; the monitor's unit tests use a controlled clock.

`GardenSnapshotSender` sends a four-fragment window, retains frames under local queue backpressure, validates peer-bound ACKs, retries every 750 ms up to five transmissions, and releases state on retry exhaustion, transport change, or disconnect. A returning player stays RECONNECTING until a matching PVZR transfer/garden/tick confirmation arrives; the client applies to its owned isolated Board, then waits for PVZK before enabling local commands. A disconnect during transfer returns it to DISCONNECTED for a fresh attempt. Unit tests cover session transitions and confirmation frame validation, but the manager lifecycle and initialized-Board behavior are not engine-tested.

## Engine extraction plan

- Inventory all `mBoard`, `gLawnApp`, render, update, effects, audio, save, random, and input dependencies.
- Introduce an explicit garden context for per-board scene/result state and simulation services currently reached through `LawnApp` globals; keep single-player bound to a one-garden context first.
- Finish separating simulation tick from `Widget::Update`/draw, gate input to the viewed board, and route effects, level completion, save, and random state to garden-owned or session-owned services.
- Add a single-player regression harness before introducing a second simulation instance.
- Validate the manager with legal game data, then continue scoping RNG, shared effects, pool effect, economy, seed selection, mode values, and result handling before treating gardens as independently simulated. Add the lobby/configuration path and a team view after this foundation is exercised in game.

## Victory rules

For Cooperative Classic, only active gardens participate. Any active garden defeat yields team defeat; team victory requires every active garden to complete. An empty roster cannot start. Disconnect state does not create or remove a garden by itself.

## Host migration

The host is authoritative in the initial design. Future migration requires a versioned full snapshot, stable entity IDs, tick/checksum agreement, and transfer of ownership/epoch to a selected peer. No migration is implemented yet.


The signaling service includes a Linux VPS deployment template: Caddy terminates HTTPS/WSS, the Node process brokers bounded room signaling, and coturn issues relay service using short-lived credentials derived from a server-only shared secret. The secret and public address are operator-supplied through an ignored `.env`; the repository contains no live endpoint or credentials. The template currently exposes UDP TURN only, so networks blocking UDP need a separately tested TCP/TLS relay path.

The signaling WebSocket server now rejects sockets above a per-instance limit of 512 connections (configurable through `createSignalingServer` for deployments/tests), in addition to its per-socket message rate limit and 32 KiB frame cap. Rejected sockets receive `SERVER_BUSY` and close with retryable code 1013.

SAVE4 reading rejects noncanonical boolean bytes (only 0 and 1), non-finite floats, selected enum/range/reference errors, malformed bounded arrays, and incomplete network chunk sets. Memory loading captures and attempts to restore a Board backup after semantic failure. This validation is still incomplete and engine rollback is unverified; do not claim hostile-host snapshot recovery is proven.

`DataReader::OpenMemory` resets the in-memory cursor on every buffer assignment. The standalone cooperative test target links the small `DataSync.cpp` reader surface so malformed boolean bytes are exercised through the actual decoder; noncanonical 0/1 encodings are rejected before writing into a C++ `bool` object.

Before SAVE4 reads variable arrays or allocates each seed-packet field blob, it validates the count against the fixed destination capacity and available input bytes. Related-zombie counts, grid-item motion-trail counts, trail point counts, resource IDs, and serialized ID-list lengths are bounded before use. Particle emitter and particle list IDs are checked against active `DataArray` entries, duplicate IDs are rejected, particle crossfade references are checked, and emitter-definition indexes are validated before access. This closes specific out-of-bounds and allocation-bomb paths; remaining field semantics/reference checks and transactional application are still required before network use.

### Deferred garden service lifetime

Each isolated Board retains shared ownership of its temporary profile, effect system, pool effect, and RNG until its destructor completes. `SafeDeleteWidget` defers Board destruction, so clearing the garden manager's collection must not invalidate pointers consumed by the Board's scoped destructor.

Cooperative Boards ignore the legacy typing-code path, which can toggle gameplay cheats, alter application-wide slow/fast motion, or locally skip a wave. Their per-board speed control is hidden and disabled because independent local time scaling would diverge garden simulation. Ordinary keyboard input still follows the regular Board input path.

Pause state is not synchronized in the current protocol. While a cooperative manager is active, `CanPauseNow`, `DoPauseDialog`, `ModalOpen`, and `ModalClose` therefore do not pause or resume only the locally viewed Board. This keeps the other clients' authoritative simulation from advancing against a locally frozen garden. Non-pause modal screens can still open while the simulation continues.

The debug `KeyChar` path is also rejected for isolated Boards, including debug builds where those hidden development cheats are otherwise enabled. This closes a local state-mutation path outside the player-command processor.

The alternate `mTodCheatKeys` mouse shortcut that advances a survival wave is also suppressed for isolated Boards; it mutates local wave timers outside the command protocol.
