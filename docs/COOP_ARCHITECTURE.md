# Cooperative architecture

## Current engine boundary

The original game is centered on `LawnApp::mBoard`, a single `Board*`. `Board` is a large `Widget` that owns fixed-capacity data arrays for plants, zombies, projectiles, coins, lawn mowers, and grid items. Board construction assigns itself to `LawnApp::mBoard`; much of the engine, UI, save code, and global helpers dereference that pointer. `LawnApp::UpdateFrames` invokes the `WidgetManager`, whose widget traversal calls `Update` on every registered board and draws visible widgets. This means widget registration could advance multiple boards, but it also exposes every board to global scene/result state and app-global effects. Merely creating or hiding multiple `Board`s would therefore render incorrectly and cross-wire gameplay state.

The board and app share `mGameScene`, `mBoardResult`, `mGameMode`, `mEffectSystem`, `mPoolEffect`, `mPlayerInfo`, and game-end/save flow. `Board::Update` mixes presentation updates, input/cursor handling, shared effects, and the simulation calls `UpdateGameObjects`, spawning, fog, challenges, and level-end transitions. Entity objects do hold an owning `Board*`, which is a useful starting boundary. A source scan found 66 direct `mApp->mBoard`/`gLawnApp->mBoard` references and 54 `gLawnApp`/global declarations across engine sources; the wider `mBoard` token count includes per-entity and widget owner fields and is not an estimate of edits required.

## Intended separation

1. `CoopSession` owns dynamic player slots and one logical `GardenInstance` for each joined player. Empty slots own no garden. Player and garden identities are stable IDs, not player-number fields.
2. The engine adapter will associate each garden with isolated simulation state. A garden's entities, economy, wave state, ownership, defeat state, and random stream must not be shared with another garden.
3. A session tick advances every active garden independently of which garden is currently displayed. The selected garden is a presentation concern only.
4. Input becomes validated player commands. A transport interface carries versioned commands and snapshots; the authoritative host applies them through the same gameplay command path used by local play. `LocalTransportHub` is the deterministic test transport. `TcpNetworkTransport` adds a bounded, ordered stream for LAN experiments, but its identity handshake is unauthenticated and its payload is unencrypted; never expose it as an Internet-ready transport.
5. The online provider is an adapter behind transport/session interfaces. Provider identity, relay, lobby, and reconnect do not enter `Board` gameplay rules.

## Phase 1 slice in this revision

`src/Coop/CoopSession.*` is an engine-independent roster and garden-ownership core. Its garden records deliberately contain only session-level identity and terminal/tick metadata; `CoopGardenManager` creates their Board instances at match start. The unit tests establish counts 1 through 4, no garden for empty slots, capacity, duplicate identity, leave, host promotion, ready/start rules, and slot reuse invariants. The host is the first joiner, and only the host can start once all active players are ready; empty slots do not block start. During a match the model records per-owner completion or defeat: any defeated garden yields team defeat, while victory requires every active garden complete. Lobby leave is rejected after start so it cannot silently delete a playing garden. Session-level disconnect/temporary-AI/reconnecting transitions preserve the slot and garden and survive session-snapshot serialization. During a match the host also detects a peer missing from the transport and broadcasts the DISCONNECTED session state to connected clients. Transport rejoin, heartbeat/grace timing, and AI control are not implemented. `Board::UpdateSimulation()` now holds the existing gameplay-tick portion of `Board::Update()` behind an explicit call, while the normal widget path invokes it once in the same place as before. That method still reads app-wide scene, effect, and widget state; it is not yet proven safe as a multi-garden driver. No gameplay regression can be manually ruled out until legal game data is available.

During a co-op match, `Tab` advances the local camera to the next active garden, wraps to the first active garden, and never creates or selects an empty slot. This view change is local; the command executor still requires the local player to own the controlled garden.

`src/Coop/PlayerCommand.*` defines transport-independent gameplay intent and checks sender state, garden ownership, protocol version, monotonic command sequence, grid bounds, enum/value ranges, and target IDs. `AuthoritativeCommandProcessor` invokes an `IPlayerCommandExecutor` only after structural validation; `CoopGardenManager` implements the executor and routes supported classic-mode actions to the owned Board after checking live state through existing engine paths. On the host, local seed selection, plant placement, shoveling, and sun clicks now generate these same commands; garden ownership rejects local attempts against another player's Board. Garden viewing is a local-only presentation action: it validates the local player's owned source garden and the active target, then changes only that client's selected view; the command helpers refuse to send or broadcast it. `CoopGardenManager::AttachTransport` binds a peer to its local session player ID; guest-side Board input serializes and sends gameplay commands to the host, and the active host pumps its receive queue before each engine simulation tick. The host increments one session tick for every active garden on each game update. For a valid remote command, the host broadcasts the accepted intent to other peers and sends its originator a fixed-size authority response carrying accepted intent and garden tick; rejected intents receive an explicit rejection reason and tick. Clients accept the authority response only from the host and apply its accepted intent once. Accepted PING intents now appear as a short named alert on each client's currently viewed Board advice widget; ping type and optional garden coordinates are validated before host broadcast. These responses do not yet provide retransmission, checksums, snapshots, or drift recovery; the path is not yet a playable network match. Board-backed gameplay still needs runtime validation with legal game data. The current fixed command/response frames and in-memory transport are not a LAN or Internet protocol stack.

`Board` now has an opt-in isolated scene/result pair. `Board::UpdateSimulation()` uses an RAII context to temporarily bind `LawnApp::mBoard`, `mGameScene`, and `mBoardResult` to a non-viewed isolated board, then restores the previously viewed board. Isolated non-viewed widgets skip cursor/UI work and call only their simulation update. `InitLevel`, `StartLevel`, board disposal, destruction, and construction of a secondary Board bind or temporarily assign the correct Board context; the constructor binding is needed because child `CutScene` and object instances capture `LawnApp::mBoard`. Non-isolated boards continue to read and write the original app fields, preserving the single-player path.

`CoopGardenManager` creates exactly one isolated `Board`, `EffectSystem`, pool water effect, and Mersenne Twister stream for each session garden, registers those boards with the widget manager, selects one visible board, cleans up the full set, and processes each board/effect delete queue. Only the host turns Board terminal results into session garden completion/defeat and broadcasts the changed session snapshot; clients wait for that authoritative state before ending the team match. A versioned session snapshot carries the host-selected match seed; each garden derives a repeatable stream from that seed and its stable owner/garden IDs. Scoped Board update, simulation, draw, initialization, and teardown bind the app/global effect pointers, pool effect, and random stream to that garden and restore the previous context afterward. The ordinary app effect system and random stream remain available to menu/UI and single-player code. `LawnApp` owns the manager, routes cooperative teardown through it, and suppresses single-board campaign end handling while the manager is active. The Game Selector's Co-op Online button opens `CoopLobbyDialog`; the dialog can create a TCP host, join a host by IP, show four dynamic player slots, select map and starting-sun difficulty, toggle ready, and start/leave. On start, `LawnApp::StartCoopMatch` maps the host-selected map to a campaign level, sets a six-plant deck, and initializes one Board per session garden. Six Classic difficulty profiles currently select starting sun; the amount receives a small adjustment based on active garden count. The app temporarily swaps in a synthetic profile and restores the original profile on exit; cooperative boards cannot write campaign saves or persist the sandbox profile. Team terminal results stop the session and return to the menu. The bootstrap currently accepts only Classic mode. Economy services, enemy balance, seed selection, and several app-global mode values remain shared, so this remains an early engine adapter and not proof of independent gameplay. Actual multi-board execution has not been tested with legal game data.

`LobbyProtocol.*` is an engine-independent host/client lobby request path layered over `INetworkTransport`. A client sends JOIN with its transport identity and bounded display name, then READY/UNREADY or LEAVE; a host-authorized START transitions the shared session. The host publishes a versioned session snapshot after lobby changes, and clients bind the snapshot source to the expected host before applying it. The snapshot includes bounded map, difficulty, and mode IDs. Only the host can change those settings, and the host freezes them at match start. Host kick and client leave remove the lobby garden and close the corresponding peer link. `CoopLobbyController` wraps local and network transports, pumps the protocol, accepts dynamic TCP guests, and applies pre-match disconnect cleanup. `CoopLobbyDialog` exposes Create/Join/Ready/Start/Leave, LAN TCP and optional Internet WebRTC modes, map and six difficulty settings. The online mode requires an operator-supplied WSS signaling endpoint; optional STUN/TURN endpoints and the TURN shared secret are configured on the signaling server, which issues short-lived per-player credentials. No public service is deployed.

The WebRTC signaling service keeps a disconnected guest's slot reserved and stores a hash of its random resume token. `CoopLobbyController` retains the room URL/code and resume token, retries `WebRtcSignalingTransport::RejoinRoom` asynchronously once the host peer disappears, validates the returned local/host IDs, rotates its token, replaces the active transport, and exposes connection diagnostics. `LawnApp` pumps this reconnect path, while `CoopGardenManager` detects transport replacement, reattaches, and the host transitions the returning roster slot back to `PLAYING` and broadcasts session metadata. The process test exercises the controller path and sends a packet over the replacement DataChannel under the existing player ID. This does not restore the departed client's complete Board runtime: entities, resources, cooldowns, wave state, and effects still need a bounded authoritative snapshot and apply path. Signaling reconnection has only been tested against a local service, not between distinct Internet networks.

`CoopSnapshotProtocol.h` provides bounded garden-snapshot fragmentation and reassembly (12 MiB cap, transport-sized chunks, out-of-order/duplicate handling, and corruption checksum). `GardenSnapshotSender` binds to a connected peer identity, queues a bounded number of frames per pump, retains a frame when `SendTo` reports backpressure, and releases pending data if the peer or transport identity changes. A two-peer test sends and reassembles a real multi-frame payload under queue pressure. This transfer sender is not yet connected to `CoopGardenManager`, and snapshot reception is not connected to Board state. The existing `SaveGame.cpp` V4 writer serializes board chunks and the effect holders currently bound by the garden context. It exposes byte serialization and exact-size memory loading in addition to the existing file APIs. The reader preflights all outer chunk framing, versions, canonical order of known chunks, duplicate chunks, and the required base chunk before applying any chunk; it caps the complete payload at 64 MiB and TLV blob/item allocations and writes, checks fixed `DataArray` metadata against the Board's allocated capacity before iterating, verifies active entry IDs and the complete acyclic free-list chain, rejects malformed item framing, and requires each known chunk's field reader and nested TLV field to consume its full payload. A nested sync error now invalidates the containing chunk instead of being swallowed. Before application it captures a bounded SAVE4 backup; if semantic decoding or required reanimation-reference validation fails, it attempts to restore the prior Board state. Loading is rejected before mutation if the backup cannot be serialized. Current semantic checks include scalar encodings, selected entity enum domains, image resource IDs, particle-system emitter/particle lists, crossfade references, emitter-definition indexes, required mower/special-zombie reanimation references, seed-bank count/cursor-slot and packet-slot identity bounds, wave cursor/count relationships, board background/grid/row/wave-zombie enum ranges, and nested plant/seed/grid-item/coin enum domains. Seed validation permits documented special seeds but rejects the `NUM_SEED_TYPES` sentinel. This still does not validate every serialized scalar/reference, and rollback failure has no secondary recovery mechanism. The memory-load API remains unsuitable for untrusted network payloads. Do not send SAVE4 bytes as reconnect snapshots until complete field-level validation and rollback behavior are proven against initialized Boards. Existing single-player save IDs and formats remain unchanged.

SAVE4 plant entities validate `mPlantCol` and inherited `mRow` against the fixed 9×6 board because gameplay reads them as grid-array coordinates. Seed packets require each saved `mIndex` to match its fixed slot, in addition to the cursor's active-slot check. Active mowers, selected special zombies, Stinky, portals, and rakes must resolve their required reanimation IDs before post-load repair. Zombie related/follower IDs must be null or resolve to active zombies before code paths that use `ZombieGet`. These checks run after the complete Board and effect-holder state is decoded and trigger the backup restore path on rejection.

GridItems also validate both coordinates against the 9×6 board, and lawn mowers validate their row before any gameplay loop can use them to index row state.

Challenge SAVE4 state validates its state and conveyor-seed enums, permits only an unset `(-1, -1)` or in-board challenge coordinate, and checks saved challenge/cloud reanimation IDs after effect holders load. Custom Survival's saved background is restricted to known board backgrounds.

MessageWidget styles and saved Music tune/file/burst/drum enums are range checked as well. Invalid presentation or audio state rejects the load instead of entering engine switches with unknown values.

Each SAVE4 attachment is limited to `MAX_EFFECTS_PER_ATTACHMENT` active entries, and each active entry's effect type must be a known enum before the engine's attachment switch runs. Attachment target IDs use `DataArrayTryToGet` and remain subject to cleanup if their target has expired.

After all SAVE4 chunks are applied, optional plant, zombie, projectile, coin, GridItem, and cursor entity/effect references must be null or resolve in the loaded Board/effect holders. Projectile target resolution follows its plant/zombie discriminator. This guards strict engine getters and keeps corrupt cross-entity IDs from surviving post-load repair.

`HeartbeatMonitor` adds a transport-level liveness frame handled before gameplay-command decoding. It sends bounded PING/PONG sequence frames, accepts only matching recent PONGs as activity, rate-limits new remote PINGs, and times out peers after 8 seconds. `CoopGardenManager` closes timed-out links; existing roster reconciliation marks the slot disconnected and preserves the garden for rejoin. This detects silent links but does not authenticate, apply a grace-state AI, or restore Board state. The heartbeat monitor and session loop use a real monotonic clock; the monitor's unit tests use a controlled clock.

`GardenSnapshotSender` builds on the bounded fragment assembler. It captures and binds the sender/recipient transport IDs at transfer start, sends a four-fragment window, preserves unsent data under local queue backpressure, and requires a versioned ACK from the expected peer before completion. Unacknowledged fragments retry every 750 ms, at most five transmissions each; retry exhaustion, transport identity changes, and disconnect release pending data. `CoopGardenManager` starts a transfer when an authenticated same-ID rejoin returns, serializing only that player's owned Board. Its packet router directs PVZS fragments to a receiver bound to the expected host, local player, and owned garden; PVZA ACKs route to the sender bound to that recipient. Before sending the final fragment ACK, the receiver runs a pure SAVE4 structural preflight (exact header size, version, 64 MiB cap, CRC, canonical chunk order, and bounded TLV framing). Invalid payloads remain unacknowledged through retries. The client applies completed bytes to its owned isolated Board through `Board::RestoreCooperativeSnapshot`, whose SAVE4 loader captures a bounded backup and restores it after semantic/reference failure. Only after success does the client send PVZR, bound to transfer, garden, and server tick; the host answers PVZK and releases its command gate, then the client releases its own gate. PVZR retries while the client awaits PVZK. Failures retain the command gate and expose a recovery error. Tests cover message serialization and the snapshot protocol, but no engine-level test instantiates the manager or restores an initialized Board. Legal game resources are unavailable here, so in-game rollback and full rejoin remain unverified.

## Engine extraction plan

- Inventory all `mBoard`, `gLawnApp`, render, update, effects, audio, save, random, and input dependencies.
- Introduce an explicit garden context for per-board scene/result state and simulation services currently reached through `LawnApp` globals; keep single-player bound to a one-garden context first.
- Finish separating simulation tick from `Widget::Update`/draw, gate input to the viewed board, and route effects, level completion, save, and random state to garden-owned or session-owned services.
- Add a single-player regression harness before introducing a second simulation instance.
- Validate the manager with legal game data, then continue scoping RNG, shared effects, pool effect, economy, seed selection, mode values, and result handling before treating gardens as independently simulated. Add the lobby/configuration path and a team view after this foundation is exercised in game.

## Victory rules

For Cooperative Classic, only active gardens participate. Any active garden defeat yields team defeat; team victory requires every active garden to complete. An empty roster cannot start. Disconnect state does not create or remove a garden by itself.

## Host migration

The host is authoritative in the initial design. Future migration requires a versioned full snapshot, stable entity IDs, tick/checksum agreement, and transfer of ownership/epoch to a selected peer. No migration is implemented yet.


The signaling service includes a Linux VPS deployment template: Caddy terminates HTTPS/WSS, the Node process brokers bounded room signaling, and coturn issues relay service using short-lived credentials derived from a server-only shared secret. The secret and public address are operator-supplied through an ignored `.env`; the repository contains no live endpoint or credentials. The template currently exposes UDP TURN only, so networks blocking UDP need a separately tested TCP/TLS relay path.

The signaling WebSocket server now rejects sockets above a per-instance limit of 512 connections (configurable through `createSignalingServer` for deployments/tests), in addition to its per-socket message rate limit and 32 KiB frame cap. Rejected sockets receive `SERVER_BUSY` and close with retryable code 1013.

SAVE4 reading rejects noncanonical boolean bytes (only 0 and 1) and non-finite floating-point values before treating the field as valid. This catches malformed scalar encodings; it does not yet validate all enum ranges, coordinate/range invariants, cross-entity references, or provide transactional Board application. The memory loader remains unsafe for untrusted network data.

`DataReader::OpenMemory` resets the in-memory cursor on every buffer assignment. The standalone cooperative test target links the small `DataSync.cpp` reader surface so malformed boolean bytes are exercised through the actual decoder; noncanonical 0/1 encodings are rejected before writing into a C++ `bool` object.

Before SAVE4 reads variable arrays or allocates each seed-packet field blob, it validates the count against the fixed destination capacity and available input bytes. Related-zombie counts, grid-item motion-trail counts, trail point counts, resource IDs, and serialized ID-list lengths are bounded before use. Particle emitter and particle list IDs are checked against active `DataArray` entries, duplicate IDs are rejected, particle crossfade references are checked, and emitter-definition indexes are validated before access. This closes specific out-of-bounds and allocation-bomb paths; remaining field semantics/reference checks and transactional application are still required before network use.
