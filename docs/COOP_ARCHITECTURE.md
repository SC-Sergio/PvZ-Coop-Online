# Cooperative architecture

## Current engine boundary

The original game is centered on `LawnApp::mBoard`, a single `Board*`. `Board` is a large `Widget` that owns fixed-capacity data arrays for plants, zombies, projectiles, coins, lawn mowers, and grid items. Board construction assigns itself to `LawnApp::mBoard`; much of the engine, UI, save code, and global helpers dereference that pointer. `LawnApp::UpdateFrames` invokes the `WidgetManager`, whose widget traversal calls `Update` on every registered board and draws visible widgets. This means widget registration could advance multiple boards, but it also exposes every board to global scene/result state and app-global effects. Merely creating or hiding multiple `Board`s would therefore render incorrectly and cross-wire gameplay state.

`Board::UpdateAll` now keeps the selected garden's normal widget traversal inside its scoped garden state. For an isolated, non-visible garden, it respects the widget manager's update flag and per-frame update counter, advances only `Board::Update`/simulation, and skips child-widget updates. This avoids running hidden garden controls against the currently selected `LawnApp::mBoard`. The engine path is build-covered but still needs a live in-game check with legal data.

The app-level frame loop also forces exactly one update per rendered frame while a co-op manager is active. The legacy global slow-motion/fast-motion cheats could otherwise skip or multiply every Board update according to one machine's stale local debug state, causing the host to publish an unexpected tick cadence and guests to fall behind. Co-op entry saves and clears those flags/counter, and teardown restores the prior single-player values. The pure frame-rate policy preserves the original single-player 0/1/20 update behavior and is unit-tested; no asset-backed frame pacing run is available yet.

The board and app share `mGameScene`, `mBoardResult`, `mGameMode`, `mEffectSystem`, `mPoolEffect`, `mPlayerInfo`, and game-end/save flow. `mLastLevelStats` was also app-wide; isolated Boards now bind it to a garden-owned `LevelStats` record during scoped simulation, draw, initialization, and teardown. `Board::Update` mixes presentation updates, input/cursor handling, shared effects, and the simulation calls `UpdateGameObjects`, spawning, fog, challenges, and level-end transitions. Entity objects do hold an owning `Board*`, which is a useful starting boundary. A source scan found 66 direct `mApp->mBoard`/`gLawnApp->mBoard` references and 54 `gLawnApp`/global declarations across engine sources; the wider `mBoard` token count includes per-entity and widget owner fields and is not an estimate of edits required.

## Intended separation

1. `CoopSession` owns dynamic player slots and one logical `GardenInstance` for each joined player. Empty slots own no garden. Player and garden identities are stable IDs, not player-number fields.
2. The engine adapter will associate each garden with isolated simulation state. A garden's entities, economy, wave state, ownership, defeat state, and random stream must not be shared with another garden.
3. A session tick advances every active garden independently of which garden is currently displayed. The selected garden is a presentation concern only.
4. Input becomes validated player commands. A transport interface carries versioned commands and snapshots; the authoritative host applies them through the same gameplay command path used by local play. `LocalTransportHub` is the deterministic test transport. `TcpNetworkTransport` adds a bounded, ordered stream for LAN experiments, but its identity handshake is unauthenticated and its payload is unencrypted; never expose it as an Internet-ready transport.
5. The online provider is an adapter behind transport/session interfaces. Provider identity, relay, lobby, and reconnect do not enter `Board` gameplay rules.

The LAN lobby calls `TcpNetworkTransport::AcceptNextPeer(0)` from its update poll. That path now incrementally accepts and reads a fixed-size identity handshake with a one-second deadline, so a client that sends only part of its hello cannot block the game loop. The explicit timed expected-peer API remains for bounded process-test setup.

Lobby JOIN requests are idempotent for a player already in the authoritative roster. A new JOIN rejected by capacity or session state is disconnected so it cannot occupy a transport peer without owning a slot. A guest tolerates roster snapshots that arrive before its own JOIN has been admitted; after it has appeared in the roster, a snapshot removing it closes the client lobby with a visible rejection reason. A missing host transport also closes the lobby with a connection error shown in the dialog.

The lobby's Internet Create and Join actions copy their inputs into detached connection tasks. TCP DNS/connect/handshake and WebRTC room/signaling/peer negotiation therefore do not run on the UI thread. Each task returns only an owned controller and plain status/invite data through a mutex-protected shared result; the dialog adopts it on its next update. Leaving or destroying the dialog drops its result handle without capturing or touching dialog/widget state. A pending operation cannot be canceled at the transport layer yet, so its bounded negotiation may finish in the background and then close when its result is discarded (10-second room creation and 30-second Internet join deadlines; TCP connect/handshake has its own bounded socket timeout).

The active-match WebRTC rejoin worker also captures only copied credentials/configuration and a shared promise; it does not retain the controller or any UI object. Its `std::future` comes from that promise, not `std::async`, so destroying the controller does not synchronously wait for the bounded signaling attempt. If the controller has gone away, the unclaimed result is destroyed with the shared future state and closes any transport it created. A focused test holds the worker open while dropping the future and verifies destruction returns promptly; a WebRTC socket-level teardown timing test remains desirable.

## Phase 1 slice in this revision

`src/Coop/CoopSession.*` is an engine-independent roster and garden-ownership core. Its garden records deliberately contain only session-level identity and terminal/tick metadata; `CoopGardenManager` creates their Board instances at match start. The unit tests establish counts 1 through 4, no garden for empty slots, capacity, duplicate identity, leave, host promotion, ready/start rules, and slot reuse invariants. The host is the first joiner, and only the host can start once all active players are ready; empty slots do not block start. During a match the model records per-owner completion or defeat: any defeated garden yields team defeat, while victory requires every active garden complete. Lobby leave is rejected after start so it cannot silently delete a playing garden. Session-level disconnect/temporary-AI/reconnecting transitions preserve the slot and garden and survive session-snapshot serialization. The manager adds heartbeat timeouts, host rejoin detection, and snapshot restore gating; automatic grace-state AI control remains unimplemented. During a match the host broadcasts disconnect and reconnecting roster states. The host publishes `PVZT` simulation ticks, clients advance only to the latest received tick, and active roster/result snapshots preserve local tick counters; explicit garden recovery may synchronize a restored Board's tick. This pacing has unit/build coverage but no injected-latency or initialized-Board evidence. Reconnect now freezes at a shared tick and transfers every garden in sequence, but the Board restore and complete reconnect path are still unverified in-engine. `Board::UpdateSimulation()` now holds the existing gameplay-tick portion of `Board::Update()` behind an explicit manager grant, while the normal widget path invokes it once in the same place as before. That method still reads app-wide scene, effect, and widget state; it is not yet proven safe as a multi-garden driver. No gameplay regression can be manually ruled out until legal game data is available.

During a co-op match, `Tab` advances the local camera to the next active garden, wraps to the first active garden, and never creates or selects an empty slot. This view change is local; the command executor still requires the local player to own the controlled garden.

`src/Coop/PlayerCommand.*` defines transport-independent gameplay intent and checks sender state, garden ownership, protocol version, monotonic command sequence, grid bounds, enum/value ranges, and target IDs. `AuthoritativeCommandProcessor` invokes an `IPlayerCommandExecutor` only after structural validation; `CoopGardenManager` implements the executor and routes supported classic-mode actions to the owned Board after checking live state through existing engine paths. On the host, local seed selection, plant placement, shoveling, sun clicks, and Cob Cannon firing use these same commands; garden ownership rejects local attempts against another player's Board. Garden viewing is a local-only presentation action: it validates the local player's owned source garden and the active target, then changes only that client's selected view; the command helpers refuse to send or broadcast it. `CoopGardenManager::AttachTransport` binds a peer to its local session player ID; guest-side Board input serializes and sends gameplay commands to the host, and the active host pumps its receive queue before each engine simulation tick. The host increments one session tick for every active garden on each game update and publishes it in a fixed-width PVZT frame. Guests only update Boards while behind that latest host tick; a credentialed WebRTC guest that falls more than 300 ticks behind closes its peer link to request a same-ID snapshot recovery, while TCP clients catch up without forced disconnection. Stale or malformed host ticks freeze the guest and close the link. Any active recovery state keeps the guest simulation frozen and suppresses another lag-triggered disconnect until the complete snapshot batch is confirmed. Accepted intents receive a fixed-size host receipt bound to each recipient, sequence, command and future garden tick (25 ticks ahead); host and clients queue the intent and apply it immediately before the Board update for that tick. A bounded per-peer FIFO retries `SendTo` failures under local backpressure. If its 256-message/512-KiB cap is exhausted, that link closes and the reconnect snapshot path handles recovery. This input delay and host-tick pacing reduce arrival-order differences for common network latency. They do not provide rollback, end-to-end receipt acknowledgements, periodic drift correction or proof that all garden simulation state is deterministic. Board-backed gameplay and the selected delay still need runtime validation with legal game data. The current fixed command/response frames and in-memory transport are not a LAN or Internet protocol stack.

The Windows TCP process smoke now extends lobby setup through gameplay-intent authority: each guest sends a uniquely owned PING intent; the host validates and executes it through `DrainAuthoritativeCommands`, sends a direct tick-bound receipt to the author and broadcasts the canonical scheduled command to the other guests; every client validates all peer commands through `DrainReplicatedCommands`. The test covers 2–4 separate processes on loopback, but uses a recording executor and does not instantiate Boards or prove a complete match.

When a client receives an accepted canonical command that its own session/sequence validator cannot accept, `DrainReplicatedCommands` now reports that replication failure to `CoopGardenManager`. The manager marks the local garden recovery FAILED and closes the host link so the existing authenticated rejoin/full-garden snapshot path can restore canonical state. This handles stream-validation mismatch; it is not arbitrary state-drift detection.

If a queued accepted command fails when applied at its designated simulation tick, the same recovery policy now closes the affected synchronization links. A guest marks its own recovery state FAILED and closes the host link. If the host cannot apply a command, it marks every connected guest DISCONNECTED/recovery FAILED and closes those links; the host remains canonical and the guests rejoin under their reserved IDs to receive the full garden batch. This path is unit-tested at the recovery-policy level and build-covered, but still needs initialized-Board runtime evidence. It does not undo a partially applied failed action or detect unrelated simulation drift.

`Board` now has an opt-in isolated scene/result/Yeti-seen state. Garden-scoped RAII contexts temporarily bind `LawnApp::mBoard`, `mGameScene`, `mBoardResult`, `mSawYeti`, `mLastLevelStats`, and the active PlayerInfo to the isolated board, then persist mutable fields back to that Board and restore the app state. The context also selects each garden's effects, pool effect, and random stream. Each Board owns a `LevelStats` record so its start/reset and level-end mower result do not overwrite a teammate's statistics. It scopes even when the selected garden is already bound, because nested garden updates must read and write that garden's Yeti history rather than the app-wide value. `CoopGardenManager::SelectGarden` exposes the viewed garden's Yeti state to app-level result handling and restores the prior single-player value when the session stops. Isolated non-viewed widgets skip cursor/UI work and call only their simulation update. `InitLevel`, `StartLevel`, board disposal, destruction, and construction of a secondary Board bind or temporarily assign the correct Board context; the constructor binding is needed because child `CutScene` and object instances capture `LawnApp::mBoard`. Non-isolated boards continue to read and write the original app fields, preserving the single-player path.

`CoopGardenManager` creates exactly one isolated `Board`, `EffectSystem`, pool water effect, Mersenne Twister stream, and temporary `PlayerInfo` copy for each session garden, registers those boards with the widget manager, selects one visible board, cleans up the full set, and processes each board/effect delete queue. Only the host turns Board terminal results into session garden completion/defeat and broadcasts the changed session snapshot; clients wait for that authoritative state before ending the team match. A versioned session snapshot carries the host-selected match seed; each garden derives a repeatable stream from that seed and its stable owner/garden IDs. `LawnApp::StartCoopMatch` creates a fresh, deterministic sandbox profile (rather than cloning the local save) with a session-derived profile ID, the selected map level, and the completed-adventure flag. This keeps purchases, Zen Garden capacity, and coin balances from making loot or board setup differ by peer. The manager copies that same sandbox profile for each local garden. Scoped Board update, simulation, draw, initialization, and teardown bind the app/global effect pointers, pool effect, per-garden profile, and random stream to that garden and restore the previous context afterward. Profile-backed purchases and coin rewards stay within each garden's temporary copy. The ordinary app effect system, player profile, and random stream remain available to menu/UI and single-player code. `LawnApp` owns the manager, routes cooperative teardown through it, and suppresses single-board campaign end handling while the manager is active. The Game Selector's Co-op Online button opens `CoopLobbyDialog`; the dialog can create a TCP host, join a host by IP, show four dynamic player slots, select map and starting-sun difficulty, toggle ready, and start/leave. On start, `LawnApp::StartCoopMatch` maps the host-selected map to a campaign level, resolves a deterministic six-seed deck through `CoopLoadout.h`, and initializes that same deck into one Board per session garden. Each Board owns its `SeedBank`, packet cooldowns, and cursor; hidden Boards still update packets from `UpdateGameObjects` during the scoped simulation path. Six data-driven Classic difficulty profiles select starting sun and a per-garden zombie-point budget scale. Starting sun receives a small adjustment based on active garden count; the zombie-point scale is applied to each map/wave budget after the base mode and map adjustments, while fixed special-wave zombies remain fixed. The app restores the original profile on exit; cooperative boards cannot write campaign saves or persist the sandbox profile. Team terminal results stop the session and return to the menu. The bootstrap currently accepts only Classic mode and sets `GAMEMODE_ADVENTURE`; in the audited `Board.cpp`, the Crazy Dave enter/talk call is confined to the Scary Potter endless-stage transition, which the current cooperative map setup does not select. Crazy Dave state remains app-global and must be revisited before adding modes that use it. Enemy balance and several app-global mode values remain shared; map-derived decks resolve identically on every peer while packet/cursor state stays garden-local, so this remains an early engine adapter and not proof of independent gameplay. Garden startup now reserves manager capacity, records each Board before widget registration, and catches setup exceptions to run manager cleanup; app/global Board, effect-system, and player-profile pointers are restored with scoped contexts. Actual multi-board execution has not been tested with legal game data.

`LobbyProtocol.*` is an engine-independent host/client lobby request path layered over `INetworkTransport`. A client sends JOIN with its transport identity and bounded display name, then READY/UNREADY or LEAVE; a host-authorized START transitions the shared session. The host publishes a versioned session snapshot after lobby changes, and clients bind the snapshot source to the expected host before applying it. The snapshot includes bounded map, difficulty, and mode IDs. Only the host can change those settings, and the host freezes them at match start. Host kick and client leave remove the lobby garden and close the corresponding peer link. `CoopLobbyController` wraps local and network transports, pumps the protocol, accepts dynamic TCP guests, and applies pre-match disconnect cleanup. `CoopLobbyDialog` exposes Create/Join/Ready/Start/Leave, LAN TCP and optional Internet WebRTC modes, map and six difficulty settings. The online mode requires an operator-supplied WSS signaling endpoint; optional STUN/TURN endpoints and the TURN shared secret are configured on the signaling server, which issues short-lived per-player credentials. No public service is deployed.

The WebRTC signaling service keeps a disconnected guest's slot reserved and stores a hash of its random resume token. `CoopLobbyController` retains the room URL/code and resume token, retries `WebRtcSignalingTransport::RejoinRoom` asynchronously once the host peer disappears, validates the returned local/host IDs, rotates its token, replaces the active transport, and exposes connection diagnostics. `LawnApp` pumps this reconnect path, while `CoopGardenManager` detects transport replacement, reattaches, and the host transitions the returning roster slot to `RECONNECTING` and starts garden recovery. The local signaling process test now routes owner-bound gameplay intents through host authority and guest replication endpoints for 2–4 players before reconnect, then checks same-ID packet delivery on the replacement DataChannel. It does not verify recovery in an initialized game Board. Signaling and command exchange have only been tested on one machine, not between distinct Internet networks.

`CoopSnapshotProtocol.h` provides bounded garden-snapshot fragmentation/reassembly and peer-bound retry. `CoopGardenManager` drains accepted commands, freezes at one host tick, and sends an ordered snapshot batch for every session garden after same-ID reconnect. The client preflights each completed SAVE4 payload, attempts rollback-capable restoration into the corresponding isolated Board, synchronizes every garden tick, and keeps the player RECONNECTING until each PVZR/PVZK pair is confirmed. Network-memory validation requires every known chunk, while the file reader retains optional-chunk compatibility. Connection loss during recovery returns the slot to DISCONNECTED and discards the batch. The manager lifecycle, successful or rolled-back load against initialized Boards, and full hostile-payload semantic coverage remain unverified; full-game reconnect must not be considered proven.

SAVE4 plant entities validate `mPlantCol` and inherited `mRow` against the fixed 9×6 board because gameplay reads them as grid-array coordinates. Seed packets require each saved `mIndex` to match its fixed slot, in addition to the cursor's active-slot check. Active mowers, selected special zombies, Stinky, portals, and rakes must resolve their required reanimation IDs before post-load repair. Zombie related/follower IDs must be null or resolve to active zombies before code paths that use `ZombieGet`. These checks run after the complete Board and effect-holder state is decoded and trigger the backup restore path on rejection.

GridItems also validate both coordinates against the 9×6 board, and lawn mowers validate their row before any gameplay loop can use them to index row state.

Challenge SAVE4 state validates its state and conveyor-seed enums, permits only an unset `(-1, -1)` or in-board challenge coordinate, and checks saved challenge/cloud reanimation IDs after effect holders load. Custom Survival's saved background is restricted to known board backgrounds.

MessageWidget styles and saved Music tune/file/burst/drum enums are range checked as well. Invalid presentation or audio state rejects the load instead of entering engine switches with unknown values.

Each SAVE4 attachment is limited to `MAX_EFFECTS_PER_ATTACHMENT` active entries, and each active entry's effect type must be a known enum before the engine's attachment switch runs. Attachment target IDs use `DataArrayTryToGet` and remain subject to cleanup if their target has expired.

After all SAVE4 chunks are applied, optional plant, zombie, projectile, coin, GridItem, and cursor entity/effect references must be null or resolve in the loaded Board/effect holders. Projectile target resolution follows its plant/zombie discriminator. This guards strict engine getters and keeps corrupt cross-entity IDs from surviving post-load repair.

Board-level ice particle IDs and each row's fwoosh reanimation IDs are also nullable references and must resolve against the app's active particle/reanimation holders before the snapshot is accepted.

Plant potted-plant indexes must be either `-1` or inside the fixed profile array capacity before any plant update or cursor rendering can use them. The check uses the array bound, not the receiving profile's populated count, so it does not assume peer profiles share garden inventory.

Zombie attachments resolve through the active attachment DataArray. Zombie target/fireball rows, ladder columns, portal columns, bungee target columns, and projectile/mower last-portal columns retain the engine's `-1` sentinel or must fall within the fixed board dimensions. Zombie umbrella state and plant subclass enums are checked during decoding.

Board presentation state is bounded before draw: fog cell looks stay in the initialized `0..19` sprite range, cell offsets remain within their initialized `-5..4` range, and fog opacity stays `0..255`. The weighted row picker retains its fixed row IDs and finite nonnegative weights/history values. Saved board result and advice enums are also checked.

`HeartbeatMonitor` adds a transport-level liveness frame handled before gameplay-command decoding. It sends bounded PING/PONG sequence frames, accepts only matching recent PONGs as activity, rate-limits new remote PINGs, and times out peers after 8 seconds. `CoopGardenManager` closes timed-out links; existing roster reconciliation marks the slot disconnected and preserves the garden for rejoin. This detects silent links but does not authenticate, apply a grace-state AI, or restore Board state. The heartbeat monitor and session loop use a real monotonic clock; the monitor's unit tests use a controlled clock.

`GardenSnapshotSender` sends a four-fragment window, retains frames under local queue backpressure, validates peer-bound ACKs, retries every 750 ms up to five transmissions, and releases state on retry exhaustion, transport change, or disconnect. A returning player stays RECONNECTING while every active garden is sent at the frozen tick. Each matching PVZR confirms restoration of one garden; the host replies with PVZK before advancing to the next. Local commands remain gated until the final confirmation; disconnect during the batch discards it and returns the slot to DISCONNECTED for a fresh attempt. Protocol tests cover four-garden order and session-scoped allowlists, but the manager lifecycle and initialized-Board behavior are not engine-tested.

## Engine extraction plan

If a client cannot place an accepted command at its authoritative tick, the receiving client's simulation has diverged, regardless of command ownership. The client marks its own recovery status failed and closes the host link; the Internet controller then uses same-ID WebRTC rejoin and the complete garden snapshot batch. This avoids leaving that client connected in a known non-canonical state, but it is not rollback and still needs initialized-Board runtime evidence.

- Inventory all `mBoard`, `gLawnApp`, render, update, effects, audio, save, random, and input dependencies.
- Introduce an explicit garden context for per-board scene/result state and simulation services currently reached through `LawnApp` globals; keep single-player bound to a one-garden context first.
- Finish separating simulation tick from `Widget::Update`/draw, gate input to the viewed board, and route effects, level completion, save, and random state to garden-owned or session-owned services.
- Add a single-player regression harness before introducing a second simulation instance.
- Validate the manager with legal game data, then continue scoping RNG, shared effects, pool effect, economy, seed selection, mode values, and result handling before treating gardens as independently simulated. Add the lobby/configuration path and a team view after this foundation is exercised in game.

## Victory rules

For Cooperative Classic, only active gardens participate. Any active garden defeat yields team defeat; team victory requires every active garden to complete. An empty roster cannot start. Disconnect state does not create or remove a garden by itself.

## Host migration

The host is authoritative in the initial design. Future migration requires a versioned full snapshot, stable entity IDs, tick/checksum agreement, and transfer of ownership/epoch to a selected peer. No migration is implemented yet.


The signaling service includes a Linux VPS deployment template: Caddy terminates HTTPS/WSS, the Node process brokers bounded room signaling, and coturn issues relay service using short-lived credentials derived from a server-only shared secret. The secret and public address are operator-supplied through an ignored `.env`; the repository contains no live endpoint or credentials. The template currently exposes UDP TURN only, so networks blocking UDP need a separately tested TCP/TLS relay path.

The signaling WebSocket server now rejects sockets above a per-instance limit of 512 connections (configurable through `createSignalingServer` for deployments/tests), in addition to its per-socket message rate limit and 32 KiB frame cap. Rejected sockets receive `SERVER_BUSY` and close with retryable code 1013.

SAVE4 reading rejects noncanonical boolean bytes (only 0 and 1), non-finite floats, selected enum/range/reference errors, malformed bounded arrays, and incomplete network chunk sets. Memory loading captures and attempts to restore a Board backup after semantic failure. This validation is still incomplete and engine rollback is unverified; do not claim hostile-host snapshot recovery is proven.

`DataReader::OpenMemory` resets the in-memory cursor on every buffer assignment. The standalone cooperative test target links the small `DataSync.cpp` reader surface so malformed boolean bytes are exercised through the actual decoder; noncanonical 0/1 encodings are rejected before writing into a C++ `bool` object.

Before SAVE4 reads variable arrays or allocates each seed-packet field blob, it validates the count against the fixed destination capacity and available input bytes. Related-zombie counts, grid-item motion-trail counts, trail point counts, resource IDs, and serialized ID-list lengths are bounded before use. Particle emitter and particle list IDs are checked against active `DataArray` entries, duplicate IDs are rejected, particle crossfade references are checked, and emitter-definition indexes are validated before access. This closes specific out-of-bounds and allocation-bomb paths; remaining field semantics/reference checks and transactional application are still required before network use.

### Deferred garden service lifetime

Each isolated Board retains shared ownership of its temporary profile, effect system, pool effect, and RNG until its destructor completes. `SafeDeleteWidget` defers Board destruction, so clearing the garden manager's collection must not invalidate pointers consumed by the Board's scoped destructor.

Cooperative Boards ignore the legacy typing-code path, which can toggle gameplay cheats, alter application-wide slow/fast motion, or locally skip a wave. Their per-board speed control is hidden and disabled because independent local time scaling would diverge garden simulation. Ordinary keyboard input still follows the regular Board input path.

Pause state is not synchronized in the current protocol. While a cooperative manager is active, `CanPauseNow`, `DoPauseDialog`, `ModalOpen`, and `ModalClose` therefore do not pause or resume only the locally viewed Board. This keeps the other clients' authoritative simulation from advancing against a locally frozen garden. Non-pause modal screens can still open while the simulation continues.

The debug `KeyChar` path is also rejected for isolated Boards, including debug builds where those hidden development cheats are otherwise enabled. This closes a local state-mutation path outside the player-command processor.

The alternate `mTodCheatKeys` mouse shortcut that advances a survival wave is also suppressed for isolated Boards; it mutates local wave timers outside the command protocol.
