# Cooperative network protocol

Command frames and authority responses have bounded fixed-width serializers. `TcpNetworkTransport` supplies a raw trusted-LAN stream and the lobby controller runs over it. The socket peer ID is a client claim, traffic has no encryption, and this transport is not suitable for public Internet sessions; authenticated Internet relay remains future work.

## Version envelope

The current command frame is exactly 53 bytes: `PVZC` magic; little-endian protocol version (1); little-endian serialization version (1); command type; sender ID; garden ID; sequence; grid coordinates; value; entity ID; target player and garden IDs; amount. It serializes fields explicitly and never copies a C++ object layout. The decoder rejects bad magic, unsupported versions, and any frame whose length is not exactly 53 bytes. `AuthoritativeCommandProcessor` then validates command enums, identities, ownership, ranges, and sequence before passing it to the gameplay executor.

The authority response frame is exactly 82 bytes: `PVZA` magic; protocol and serialization versions; recipient player ID; echoed command sequence; authoritative garden simulation tick; rejection code; and a 53-byte command only when accepted. A rejected response must carry an all-zero command area. The decoder checks exact size, versions, rejection range, recipient/sequence binding, and accepted-command identity. Host ingress sends a direct response to the originating transport peer, broadcasts accepted intent to other peers, and the originator applies an accepted response exactly once. Host rejection is returned without executing the gameplay action. The authoritative tick is a per-garden session count advanced together for all active gardens on each game update. The tick is metadata only so far: clients do not yet use it to recover drift or order retries.

The next envelope revision must add a message type, session epoch, and bounded payload length so command, lobby, snapshot, and heartbeat messages can share the transport. It must retain a separate schema version and explicit byte order. Reject unknown required versions/types, lengths above the configured maximum, invalid enum values, and trailing/short payloads.

The command model in `src/Coop/PlayerCommand.*` uses protocol version 1, a player ID, garden ID, increasing sequence, command type, bounded coordinates/value, entity/target IDs, and amount. The validator rejects non-playing senders, unknown/non-owned gardens, duplicate or stale sequences, out-of-range grid coordinates, unknown command types, invalid ping/plant/selection values, invalid view/resource targets, and excessive resource amounts. It accepts sequence gaps but records a sequence only after structural validation succeeds. Gameplay application must still check current plant unlocks/resources, cooldowns, sun entities, and match state. `CommandSerialization.*` has round-trip and malformed-size/version tests; the authority response now reports acceptance/rejection and the canonical garden tick, but pending-command retries, tick-drift recovery, rate limiting, session epoch, and reliable socket delivery are not implemented yet.

`SessionSnapshotSerialization.*` adds a separate, fixed-schema v2, length-capped session snapshot for the four lobby slots, host identity, shared match seed, next garden ID, selected map/difficulty/mode, and garden owner/result/tick metadata. It preserves empty slots without allocating gardens and can rebuild a `CoopSession` without reusing IDs from a departed slot. The shared seed plus stable player/garden IDs initializes repeatable garden-local Mersenne Twister streams. These settings are IDs only; the game bootstrap does not consume them yet. The payload is only lobby/session metadata; it contains no `Board` entities, economy, active RNG state, seed-bank state, wave queues, or effects and therefore cannot restore an active game after reconnect. The engine's existing SAVE4 chunks cover many of those fields, but the file-path reader applies chunks incrementally; see the architecture note before reusing it for hostile packet data.

## Message families

- Lobby: create/join intent, lobby snapshot, ready state, settings request, start, leave/kick.
- Gameplay intent: place/remove plant, collect sun, select plant, ping, request view, send resource.
- Authority: accepted/rejected command with server tick and sequence; periodic full snapshot then bounded deltas.
- Liveness: ping/heartbeat, timeout, reconnect authentication, full resynchronization snapshot.

`LobbyProtocol.*` adds a bounded `PVZL` schema-v2 request frame for JOIN, READY/UNREADY, START, LEAVE, and settings. The host binds the payload player ID to the transport peer before mutating `CoopSession`; only the host can start or change settings, and leave/kick removes the peer relationship and its garden while still in the lobby. Host-authored snapshots replicate the roster and map/difficulty/mode IDs; clients only apply snapshots received from the expected host and detect when they are no longer in the roster. `CoopLobbyController` wraps host/client transport ownership, auto-accepts dynamic TCP peer identities while pumping a host lobby, applies ready and start actions, settings snapshots, kick/leave, and drops disconnected players from the roster before match start. Local tests cover setting authorization and replication; separate-process TCP smoke tests cover 3- and 4-player lobby start. The settings do not yet configure a `Board`. Room-code discovery, user-facing lobby widgets, and explicit client-visible rejection reasons remain to implement. This is an engine-independent lobby API, not a complete playable UI.

Command types modeled now: `PLACE_PLANT`, `REMOVE_PLANT`, `COLLECT_SUN`, `SELECT_PLANT`, `CHANGE_VIEW`, `PING`, and `SEND_RESOURCE`. Ping values are `DANGER`, `NEED_SUN`, `HELP`, `LOOK_HERE`, `GARGANTUAR`, and `ALL_GOOD`.

The client never submits arbitrary canonical state such as a sun total or direct entity deletion. The host validates sender/slot and garden ownership, phase, coordinates, available resources, cooldown, rate, and command ordering before applying intent. Reliable ordered delivery is required for state-changing commands; snapshots may replace stale intermediate deltas.

## Identity, ordering and recovery

Player IDs are session-scoped and distinct from slot indices. Entity and garden IDs are explicit. Sequence numbers are monotonic per sender; duplicates are idempotently rejected and stale/out-of-order commands follow a documented bounded policy. Server ticks and snapshot checksums detect drift. Reconnect reauthenticates a player, binds the original slot, and sends a bounded full snapshot before accepting commands again.

## Transport boundary

`INetworkTransport` defines a transport-neutral send/receive boundary and enumerates connected peer identities. `LocalTransportHub` is a deterministic in-memory FIFO test adapter with up to four registered peer identities, a 64 KiB message limit, and a 256-packet per-peer queue limit that rejects sends under backpressure. `TcpNetworkTransport` adds a TCP stream adapter with a four-byte little-endian length prefix, a 64 KiB frame cap, bounded packet queues, five-second client connection attempts, a one-second bounded server handshake read, nonblocking gameplay reads/writes, peer-close detection, and expected-ID or dynamic host acceptance handshakes. Separating the listener poll timeout from the handshake read timeout lets the lobby poll without rejecting simultaneous arrivals. The host binds the handshake ID to a transport peer; the ID is a client claim and is not cryptographic authentication. Tests cover a host and three guests in same-process loopback and separate host/guest processes for 3- and 4-player JOIN/READY/START with host-selected settings replicated to each client. Traffic is unencrypted. Use this adapter for trusted LAN transport experiments only, not across the public Internet. It does not provide NAT traversal or relay.

`SendCommandToHost` binds the client payload identity to its transport identity. `DrainAuthoritativeCommands` binds transport-authored sender identity to the command sender field, rejects non-host receivers and malformed frames, and routes accepted commands through validation and an executor; accepted commands are broadcast to peers other than the originator while an authority response is sent directly to the originator. `DrainReplicatedCommands` accepts gameplay frames and authority responses only from the session host, verifies the receipt recipient, and applies accepted commands once. Explicit rejection responses currently reach the caller but are not yet connected to pending-command UI or retry storage. The transport still has no full-state repair path, checksums, retransmission, or migration. `CoopGardenManager` implements the executor and routes plant, remove, sun collection, and seed selection to the owning Board, view changes to the presentation selector, and bounded sun transfers between gardens. Board-backed operations have compile coverage only; they still need gameplay tests with legal game data. Ping execution is not implemented. `LocalTransportHub` and `TcpNetworkTransport` do not simulate delay/loss/reordering or provide Internet reachability. Internet connectivity must use a separate authenticated encrypted provider/relay adapter and share command validation. Provider identity tokens and credentials must not be stored in gameplay messages or source control. Host migration is deferred and requires session epoch transfer plus a verified authoritative snapshot.
