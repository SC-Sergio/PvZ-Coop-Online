# Cooperative network protocol

Command frames and authority responses have bounded fixed-width serializers. `TcpNetworkTransport` supplies a raw trusted-LAN stream and the lobby controller runs over it. Its socket peer ID is a client claim and traffic is unencrypted, so TCP is not suitable for public Internet sessions. The optional `WebRtcNetworkTransport` adapts reliable binary DataChannels to `INetworkTransport`; a separate signaling service binds peers to room membership. No TURN relay deployment is configured yet.

## Version envelope

The current command frame is exactly 53 bytes: `PVZC` magic; little-endian protocol version (2); little-endian serialization version (2); command type; sender ID; garden ID; sequence; grid coordinates; value; entity ID; target player and garden IDs; amount. It serializes fields explicitly and never copies a C++ object layout. The decoder rejects bad magic, unsupported versions, and any frame whose length is not exactly 53 bytes. `AuthoritativeCommandProcessor` validates command enums, identities, ownership, ranges, and sequence. After sender/garden ownership checks, the host validator applies a per-player token bucket with a 32-command burst and a refill rate of 20 command attempts per second; malformed intent fields and stale/replayed sequences consume budget. Excess traffic receives `INVALID_RATE` and does not consume its sequence number. Rate state is bounded by the active roster and reset with the validator. `FIRE_COB_CANNON` uses `entityId` for the garden-local plant ID and bounded world-pixel `x/y` target coordinates; the host checks that the referenced plant is an owned, ready, non-mind-controlled Cob Cannon before firing.

The authority response frame is exactly 82 bytes: `PVZA` magic; protocol and serialization versions; recipient player ID; echoed command sequence; authoritative garden simulation tick; rejection code; and a 53-byte command only when accepted. A rejected response must carry an all-zero command area. The decoder checks exact size, versions, rejection range, recipient/sequence binding, and accepted-command identity. The host sends a direct accepted/rejected receipt to the originator and sends an accepted receipt to every other peer; the accepted command sender may therefore differ from the receipt recipient. All accepted receipts carry the same future execution tick, 25 simulation ticks ahead. Host and clients queue the command and apply it immediately before that garden's Board update at the designated tick. The tick lead gives reliable DataChannels time to deliver common-latency commands consistently. If a client cannot schedule an accepted command at its authoritative tick, that receiving client's simulation is no longer canonical; it marks its own recovery status FAILED, closes the host link, and uses the same-ID WebRTC rejoin and full garden snapshot path. This is bounded input delay and reconnect recovery, not rollback or general drift correction.

If the accepted command instead fails during application at its designated tick, a guest closes its host link and requests the same recovery path. If the host's application fails, it keeps the authoritative session and marks/closes each connected guest link so every guest reconnects and receives a complete authoritative garden batch. The failed command has already been removed from the scheduled queue; this policy does not roll back partial effects or guarantee recovery if the host's own state was corrupted.

The host also publishes a fixed 16-byte `PVZT` simulation-clock frame: magic at bytes 0–3, protocol version 1 at byte 4, zero reserved bytes at 5–7, and the unsigned little-endian host tick at 8–15. Clients accept it only from the session host, reject malformed frames and disconnect on a stale tick, and update isolated Boards only while their local tick is below the latest published host tick. A client transport advertises whether it has authenticated same-session resume credentials. When such a client falls more than 300 ticks behind, it closes the host peer link to enter the existing reconnect and full garden snapshot batch; transports without rejoin support keep catching up on their current link. Roster/result snapshots during an active match preserve local simulation ticks; only the explicit garden-restore path may change a restored garden's tick. This paces clients against the host under ordinary latency. It does not roll back a late command or detect arbitrary state drift.

The garden manager routes command frames and receipts through a per-peer FIFO send queue when `INetworkTransport::SendTo` reports local backpressure. It retains at most 256 messages and 512 KiB per peer, pumps retries before processing each game update, and discards pending messages for peers no longer connected. If a command or receipt cannot be retained within those caps, the manager disconnects that peer so the existing disconnect/rejoin snapshot path can restore it. On a replaced client transport, old local scheduled commands are discarded; accepted receipts received during full-batch recovery are validated for sequence but not replayed because the authoritative snapshots already include their effects. Once `SendTo` accepts a frame, the underlying TCP or reliable WebRTC transport is responsible for delivery; this queue is not an end-to-end acknowledgement protocol.

`PING` uses the command's `value` field for `PingType` values 0–5 (`DANGER`, `NEED_SUN`, `HELP`, `LOOK_HERE`, `GARGANTUAR`, `ALL_GOOD`). Coordinates must either both be `-1` or both fall within the 9×6 board. The host validates and broadcasts accepted pings; each client displays a short alert on its currently viewed garden with the sender's display name, source garden ID, local simulation tick timestamp, and optional one-based board coordinates.

The next envelope revision must add a message type, session epoch, and bounded payload length so command, lobby, snapshot, and heartbeat messages can share the transport. It must retain a separate schema version and explicit byte order. Reject unknown required versions/types, lengths above the configured maximum, invalid enum values, and trailing/short payloads.

## Prepared garden snapshot fragments

`CoopSnapshotProtocol.h` defines an explicit `PVZS` fragment frame, separate from the command/lobby envelope and routed by `CoopGardenManager`. All integer fields are little-endian. The 44-byte header is: bytes 0–3 magic; 4–5 protocol version (1); 6–7 header size (44); 8–15 transfer ID; 16–19 garden ID; 20–27 authoritative server tick; 28–31 total snapshot bytes; 32–33 chunk count; 34–35 chunk index; 36–39 whole-snapshot FNV-1a 32-bit checksum; 40–41 chunk payload bytes; 42–43 reserved zero. Chunk data follows at offset 44. Each chunk is at most `MAX_TRANSPORT_MESSAGE_BYTES - 44`; a transfer is capped at 12 MiB and uses fixed offsets/sizes, with a single bounded in-progress assembly per `GardenSnapshotAssembler`.

The assembler supports out-of-order chunks and identical duplicates, rejects conflicting metadata, invalid indexes/sizes and checksum mismatch, and releases its buffer after completion or checksum failure. FNV-1a detects accidental/corrupt transfer data only; peer authentication and confidentiality come from the transport, and the checksum is not a security mechanism. `GardenSnapshotSender` uses a fixed window of four chunks and the `PVZA` 24-byte ACK frame (magic, version, frame size, transfer ID, garden ID, chunk index, reserved zero). The sender accepts an ACK only from the bound recipient and only for a chunk already sent in that transfer. It retries each unacknowledged chunk after 750 ms and stops after five attempts. `CoopGardenManager` starts an ordered recovery batch after authenticated same-ID rejoin. The host drains already accepted commands, freezes the shared simulation at one tick, and sends every active garden sequentially. The receiver accepts frames only from the expected host and for a garden ID in the current bounded session roster, and runs SAVE4 structural preflight before acknowledging the final fragment. Invalid completed transfers receive no final ACK, including on duplicate retries. After the exact-length, schema, size, CRC, chunk-order, and TLV checks, the client loads bytes into the matching isolated Board using the SAVE4 rollback wrapper. It then sends a fixed 30-byte `PVZR` completion frame containing transfer ID, garden ID, and server tick. The host validates that tuple against the current garden in the recovery batch and replies with the same `PVZK` frame before sending the next garden. Both sides keep gameplay commands gated until every garden transfer has been acknowledged; only then does the host return the player to PLAYING and resume simulation. The client retries `PVZR` every 750 ms until acknowledged. This path is build- and protocol-tested but has not been exercised with initialized game Boards; field/reference semantics, rollback behavior, and full reconnect in the engine still require legal game data and runtime testing.

The command model in `src/Coop/PlayerCommand.*` uses protocol version 2, a player ID, garden ID, increasing sequence, command type, bounded coordinates/value, entity/target IDs, and amount. The validator rejects non-playing senders, unknown/non-owned gardens, duplicate or stale sequences, out-of-range grid coordinates, unknown command types, invalid ping/plant/selection values, invalid view/resource targets, and excessive resource amounts. `COLLECT_SUN` and `COLLECT_COIN` carry board-local entity IDs; the host distinguishes sun entities from other collectible coins before applying the existing collection path. It accepts sequence gaps but records a sequence only after structural validation succeeds. A per-player token bucket limits command attempts to a burst of 32 and a refill of 20 per second. Gameplay application must still check current plant unlocks/resources, cooldowns, coin state, and match state. `CommandSerialization.*` has round-trip and malformed-size/version tests; authority responses report acceptance/rejection and the canonical garden tick, and a bounded FIFO retries local `SendTo` backpressure. TCP and the default WebRTC DataChannel are reliable ordered transports. There is no application-level command receipt ACK/retry, tick-drift recovery, or session epoch yet.

SAVE4 now has a 64 MiB payload cap, requires known chunks in canonical ascending order, and checks particle/emitter list IDs, particle crossfade IDs, and emitter-definition indexes before decoder-side dereferences. Unknown future chunks remain skippable. The network-memory API additionally requires every known chunk, preventing partial updates from retaining stale garden state; the file reader preserves optional-chunk compatibility. The V4 memory loader captures a bounded pre-load Board backup and attempts to restore it after semantic/reference failure. That rollback is not yet demonstrated against an initialized Board; the network path uses it but keeps commands gated on any load failure.

Zombie and projectile SAVE4 readers also validate inherited `GameObject::mRow` against the board's six rows before simulation can use it to index row arrays. Helper boundary tests cover negative, lowest valid, highest valid, and one-past-end values. The guard is compiled into both Debug builds; initialized-Board restore still needs legal game data for runtime verification.

Portable plant and projectile state also bounds `mStartRow` and `mCobTargetRow` to the board and validates the optional torchwood column (`-1` or a board column). This prevents a peer-provided garden snapshot from restoring these gameplay indices out of range before simulation resumes.

Zombie wave origin values are bounded to wave slots or the engine's four reserved negative origins (`-1` through `-4`); arbitrary values are rejected during SAVE4 entity decoding.

SAVE4 world positions and pixel targets are bounded to ±10,000 pixels, with object extents bounded to 0–10,000. The margin keeps legitimately off-screen entities representable while preventing extreme finite peer-provided coordinates from reaching integer conversion and geometry code. The bounds cover base GameObject geometry, plant targets, zombie/projectile/coin/mower/GridItem positions, collision rectangles, particle/trail vectors, and attachment/reanimation matrices; runtime compatibility still requires initialized-Board testing.

`SessionSnapshotSerialization.*` adds a separate, fixed-schema v2, length-capped session snapshot for the four lobby slots, host identity, shared match seed, next garden ID, selected map/difficulty/mode, and garden owner/result/tick metadata. It preserves empty slots without allocating gardens and can rebuild a `CoopSession` without reusing IDs from a departed slot. The shared seed plus stable player/garden IDs initializes repeatable garden-local Mersenne Twister streams. The current bootstrap consumes map IDs and three difficulty presets; only Classic mode is accepted. The payload remains lobby/session metadata; it contains no `Board` entities, economy, active RNG state, seed-bank state, wave queues, or effects and therefore cannot restore an active game after reconnect. The engine's existing SAVE4 chunks cover many of those fields, but the file-path reader applies chunks incrementally; see the architecture note before reusing it for hostile packet data.

## Message families

- Lobby: create/join intent, lobby snapshot, ready state, settings request, start, leave/kick.
- Gameplay intent: place/remove plant, collect sun or a non-sun coin, select plant, fire a Cob Cannon, ping, request a local view change, and send resources.
- Authority: accepted/rejected command with server tick and sequence; periodic full snapshot then bounded deltas.
- Liveness: ping/heartbeat, timeout, reconnect authentication, full resynchronization snapshot.

The separate `services/coop-signaling` WebSocket service accepts ephemeral room create/join and relays host↔guest SDP offers and answers. It caps rooms at four identities, binds sender IDs to WebSocket connections, limits payloads and message rate, bounds each socket's queued output to 256 KiB, and does not carry gameplay traffic. A slow consumer is closed before more messages are added to its queue. Host leave closes the room and connected guest sockets so stale sessions do not consume the server's connection cap. The C++ client uses full gathered SDP (rather than trickle ICE) and the service can also forward candidates. The local process test now uses the resulting DataChannels for command receipts and broadcasts with 2–4 players; this checks endpoint interoperability, not NAT traversal. See that service's README for its wire envelope and local run commands.

`LobbyProtocol.*` adds a bounded `PVZL` schema-v2 request frame for JOIN, READY/UNREADY, START, LEAVE, and settings. The host binds the payload player ID to the transport peer before mutating `CoopSession`; only the host can start or change settings, and leave/kick removes the peer relationship and its garden while still in the lobby. Host-authored snapshots replicate the roster and map/difficulty/mode IDs; clients only apply snapshots received from the expected host and detect when they are no longer in the roster. `CoopLobbyController` wraps host/client transport ownership, accepts dynamic TCP peers, applies ready/start/settings snapshots and drops disconnected players before match start. With the optional WebRTC feature compiled, `CoopLobbyDialog` also creates a private signaling room or joins by the host's invite URL; the signaled host/guest transport runs the same lobby protocol. LAN TCP still joins by IP/port 28457. Local separate-process TCP tests cover 2/3/4-player lobbies and authoritative command exchange. A Node signaling process test covers WebRTC 2/3/4-player lobby start, canonical command exchange, EMPTY-slot preservation, and same-ID guest rejoin. This is a locally tested connection path, not yet a cross-network Internet service: deployment, STUN/TURN setup, distinct-network NAT traversal and real game play remain unverified.

Command types modeled now: `PLACE_PLANT`, `REMOVE_PLANT`, `COLLECT_SUN`, `COLLECT_COIN`, `SELECT_PLANT`, `CHANGE_VIEW`, `PING`, `SEND_RESOURCE`, and `FIRE_COB_CANNON`. Ping values are `DANGER`, `NEED_SUN`, `HELP`, `LOOK_HERE`, `GARGANTUAR`, and `ALL_GOOD`.

The client never submits arbitrary canonical state such as a sun total or direct entity deletion. The host validates sender/slot and garden ownership, phase, coordinates, available resources, cooldown, rate, and command ordering before applying intent. Reliable ordered delivery is required for state-changing commands; snapshots may replace stale intermediate deltas.

The Windows TCP process smoke runs one host plus one to three guests through lobby start, then sends one unique PING intent from each guest. The host uses the production command decoder/authority processor, returns an accepted receipt with the 25-tick execution point to the sender, and broadcasts each scheduled canonical command to the other guests. Every guest uses the production replicated-command validator and checks the sender's garden binding, sequence, and tick. This proves localhost transport and endpoint exchange for 2–4 processes; it does not apply commands to a Board or prove LAN/Internet delivery.

## Identity, ordering and recovery

Player IDs are session-scoped and distinct from slot indices. Entity and garden IDs are explicit. Sequence numbers are monotonic per sender; duplicates are idempotently rejected and stale/out-of-order commands follow a documented bounded policy. Server ticks pace guest simulation, while the snapshot checksum only detects corruption within a single transfer; the protocol does not yet detect or repair arbitrary live state drift. Reconnect reauthenticates a player, binds the original slot, and starts a bounded batch covering every active garden. The host drains accepted commands and freezes simulation at one tick, then retains RECONNECTING state and rejects new gameplay commands until it has received a matching PVZR restore confirmation for every garden. The client applies each authenticated snapshot to the corresponding session Board and keeps its local command gate until the final PVZK arrives. Engine-level reconnect behavior remains unverified with initialized Boards.

If a client receives a host-accepted command but its local session/command validator rejects that canonical action, it closes the host link and enters the same-ID full-snapshot rejoin path. This repairs a known stream-validation mismatch; it does not detect arbitrary entity or economy divergence when commands still validate locally.

## Transport boundary

The TCP lobby poll uses `AcceptNextPeer(0)` as an incremental operation: it accepts at most a bounded number of pending sockets, reads the fixed eight-byte identity hello without blocking, and drops incomplete handshakes after one second. A partial hello therefore does not stall lobby rendering or network pumping. The timeout-based expected-ID helper remains a blocking test/setup API and is not used by the lobby update loop.

`INetworkTransport` defines a transport-neutral send/receive boundary and enumerates connected peer identities. `LocalTransportHub` is a deterministic in-memory FIFO test adapter with up to four registered peer identities, a 64 KiB message limit, and a 256-packet per-peer queue limit that rejects sends under backpressure. `TcpNetworkTransport` adds a TCP stream adapter with a four-byte little-endian length prefix, a 64 KiB frame cap, bounded packet queues, five-second client connection attempts, a one-second bounded server handshake read, nonblocking gameplay reads/writes, peer-close detection, and expected-ID or dynamic host acceptance handshakes. Use TCP only on trusted LANs. Optional `WebRtcNetworkTransport` adapts a reliable binary `rtc::DataChannel` per peer, caps payload/queue sizes, binds each channel to the signaling-provided player ID, and accepts only binary packets. `WebRtcSignalingTransport` owns the WSS/WebSocket signaling client and peer connections, creates rooms or joins a room code, applies gathered SDP, and delegates gameplay packets to that adapter. It rejects signaling frames above 32 KiB, descriptions above the relay's 32 KiB-minus-512-byte payload limit, malformed room codes, self-reported host identities, and peer signals from identities not admitted in the current room. The dialog accepts a WSS endpoint and displays a share URL; remote `ws://` is rejected, while plain WS remains available for localhost development. STUN/TURN configuration comes from runtime environment variables, not source. Local process tests exercise 2/3/4-player signaling/lobby setup, canonical command replication, and same-ID DataChannel replacement; public WSS/TURN deployment and cross-network connectivity remain unverified, so Internet availability is not claimed.

`SendCommandToHost` binds the client payload identity to its transport identity. `DrainAuthoritativeCommands` binds transport-authored sender identity to the command sender field, rejects non-host receivers and malformed frames, and routes accepted commands through validation and an executor; accepted commands are broadcast to peers other than the originator while an authority response is sent directly to the originator. `DrainReplicatedCommands` accepts gameplay frames and authority responses only from the session host, verifies the receipt recipient, and applies accepted commands once. Explicit rejection responses currently reach the caller but are not yet connected to pending-command UI or retry storage. Garden snapshot frames use bounded fragment retransmission; completed SAVE4 data is restored to each roster-bound isolated Board in a frozen-tick recovery batch, and gameplay remains gated until every PVZR/PVZK completion is confirmed. There is no state-delta repair or host migration. `CoopGardenManager` implements the executor and routes plant placement/removal, sun and coin collection, seed selection, Cob Cannon firing, bounded sun transfers between gardens, local view changes, validated PING alerts, and same-ID rejoin snapshot transfer. Board-backed operations have compile coverage only; they still need gameplay tests with legal game data. Validated PING commands show short named alerts locally on each client. `LocalTransportHub` and `TcpNetworkTransport` do not simulate delay/loss/reordering or provide Internet reachability. Internet connectivity must use a separate authenticated encrypted provider/relay adapter and share command validation. Provider identity tokens and credentials must not be stored in gameplay messages or source control. Host migration is deferred and requires session epoch transfer plus a verified authoritative snapshot.
# Liveness and heartbeat

`HeartbeatProtocol.h` defines a fixed 16-byte little-endian `PVZH` control frame (protocol version 1, message type, nonzero sequence). Peers exchange PING/PONG over the established transport every 2 seconds. Only a PONG matching one of the last four outstanding PING sequences refreshes the local peer's activity timer. New remote PING sequences are accepted at most once per second; stale sequences do not refresh liveness. Eight malformed heartbeat frames close the peer link.

After 8 seconds without a valid response, `CoopGardenManager` disconnects the transport peer. The host's existing roster reconciliation changes the slot to DISCONNECTED while retaining its slot and garden; the rejoin controller may then resume the same identity and replace the transport. A heartbeat proves reachability only: it does not authenticate a peer, protect against deliberate replay on an authenticated channel, resynchronize garden state, or itself implement retransmission/grace AI. The local signaling test covers token-authenticated WebRTC rejoin separately.
